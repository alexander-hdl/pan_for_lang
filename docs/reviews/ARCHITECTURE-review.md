# Ревью архитектуры pan_for_lang (ARCHITECTURE.md v1.0)

*Независимое рецензирование, 2026-10-13. Объект: `docs/ARCHITECTURE.md` (2743 строки, прочитан целиком). Сверка: `docs/METHODOLOGY.md` (на момент ревью файл уже содержит **v1.1**, 1608 строк, прочитан целиком), `docs/reviews/METHODOLOGY-review.md` (R01–R42), `docs/research/03-tech-stack-pen-input.md` (§1–4, 6–7, 9.4, прил. ## Как проверялось

1. **Покрытие методики.** Каталог упражнений, правила §4–§9 и журнал решений D1–D45 методики v1.1 сопоставлены с §3, §5, §6, §8, §12 архитектуры.
2. **Утверждения про API и библиотеки** проверены по первоисточникам (список в конце): `GetPointerPenInfoHistory` (порядок и время жизни истории), ограничения WPF `EnablePointerSupport`, наличие переключателя `DisableStylusAndTouchSupport` в WPF на .NET, матрица ОС .NET 10, лицензия PDFsharp и поддержка `net10.0`.
3. **Оценщик.** Пайплайн §6 прочитан как алгоритм. Для слова из 8 букв в режиме диктанта оценены размер решётки и число ячеек DP. Отдельно разобраны сценарии, на которых выравнивание ломается: пропущенное соединение, точка поставлена сразу, дорисовка, «гребёнки» m/n/u, длинные слова.
4. **План.** Граф зависимостей задач T0.x–T5.x построен заново по полям «Зависит» и «Входы». Сигнатуры §3.7, §5.3, §6.2 и §12.5 сверены с таблицей сборок §2.2 и диаграммой §2.3.

**Что даёт v0.** Проверены главные технические риски: `WM_POINTER` при отключённом стилусе, DPI на втором мониторе, задержка, базовое качество DTW на настоящем письме. Есть реальный корпус для S2. Контракты T0.2 пишутся по работающему коду. Дальше — **v0.5**: диктант `at/it/tin/sat` с локальным переоцениванием гипотез (A09) и глифами т/и/п. Затем педагогический движок (карточки, планировщик) на уже живом оценщике.

## Что сделано хорошо

- **Разделение «факты ↔ решения»** (оценщик выдаёт метрики и коды, стоповость и Leitner — в `Learner`/`Feedback` по таблицам) — правильная граница. Она позволяет калибровать педагогику без переоценки и тестировать оценщик без педагогики.
- **Стиль-пакеты с абстрактными классами E-*/X-*/JF\* и процедурными соединениями**, а также печатный стиль и «ловушки» как роли того же формата — ровно то, что требует методика §3.1. Валидация пар 26×26 и SVG-ревью снимают риск C8.
- **Тестируемость без железа**: `IPenInputSource` + `ReplayPenSource`, единый формат `penlog` для корпуса, InkLab и экспорта, `SynthInk` с размеченными мутациями, внедряемые часы и RNG. Симулятор курса — сильная идея, подтверждённая ревью методики.
- **Честная маркировка** [проверено]/[не проверено] с номером спайка, ADR-журнал, явные вопросы заказчику, вынесение порогов в конфигурацию со ссылкой на М §.
- **Надёжность и приватность по умолчанию**: SQLite WAL, транзакция на попытку, чекпойнт, копия перед миграцией, контрольные суммы миграций, отсутствие сетевого кода как архитектурный тест, согласие с версией текста.
- **Учтены почти все находки ревью методики** (R01–R04, R09–R12, R14, R18, R22, R23, R25–R27): механизмы заложены. Пробел в основном там, где v1.1 пошла дальше рекомендаций ревью (A02).

## Проверка утверждений про API и библиотеки

| Утверждение в документе | Результат |
|---|---|
| `GetPointerPenInfoHistory` отдаёт историю в обратном хронологическом порядке; забирать до следующего сообщения | **Подтверждено**: «reverse chronological order, with the most recent entry in the first row». Данные связаны с последним полученным потоком сообщением и могут пропасть после следующего; вызов из потока, не владеющего окном, — `ERROR_ACCESS_DENIED`. Значит, вызывать строго в hook на UI-потоке, без вложенных циклов сообщений между получением и чтением. |
| В pointer-режиме WPF нет real-time inking | **Подтверждено** (для `EnablePointerSupport`): плагины стилуса работают на UI-потоке, меняется продвижение в мышь. Решение архитектуры не включать этот режим верно. |
| `Switch.System.Windows.Input.Stylus.DisableStylusAndTouchSupport` | Переключатель **существует** в исходниках WPF на .NET (`CoreAppContextSwitches`). Доставка `WM_POINTER` в hook при нём по-прежнему [не проверено] — пункт S1 п. 6, это верно отмечено. |
| .NET 10 формально не поддерживает потребительскую Windows 10 22H2 | **Подтверждено** (supported-os.md: Windows 10 — 21H2 (E/IoT), 1809 (E), 1607 (E)). |
| PDFsharp 6.x — MIT, `net10.0` | **Подтверждено**: MIT, пакет 6.2.x собран в том числе под `net10.0`; в Core-сборке font resolver обязателен (A31). |

## Общий вердикт

**Архитектура сильная и в целом верная по замыслу. Утвердить её можно только с обязательными правками; заморозку контрактов (T0.2) отложить до вертикали v0.**

Документ продуманнее большинства проектных документов такого масштаба. Чистое ядро, факты отдельно от решений, стиль-пакеты, воспроизводимость, приватность, симуляция курса и тестирование без планшета выбраны правильно и хорошо обоснованы исследованием 03. Технические утверждения про ввод пера там, где их можно проверить, соответствуют документации Microsoft.

Блокирующих групп четыре:
1. **Расхождение с методикой v1.1 и решением заказчика** (A01, A02). Операционные чернила хранятся без согласия вопреки D26/FR-8. Каталог, карточки и правила нагрузки описаны по v1.0. По этой версии собираются замораживать контракты.
2. **Дыры в ядре оценщика** (A03, A04, A09). Пропущенное соединение и «точка сразу» ломают выравнивание и плодят ложные J1. Глобальное правило принятия гипотез ведёт себя по-разному в коротких и длинных словах и превращает моторные промахи (лишний горб) в стоп-ошибки выбора. Общая решётка с лучом при `maxEdits = 1` сложнее и рискованнее, чем «DTW по цели + локальное переоценивание гипотез».
3. **Недостоверный спайк S2** (A08). Синтетика из тех же глифов проверяет алгоритм на собственной модели. Набор букв не покрывает тестовые слова. Нет решающего правила. Запасной план опирается на ту же сегментацию.
4. **Водопад с поздней интеграцией** (A07, A15–A17). До первого «ребёнок пишет букву → подсказка» нужно около 30 задач, контракт оценщика замораживается до спайка, а два самодельных DSL и 20 сборок увеличивают объём там, где ценности для v1 нет.

Рекомендуемый порядок: A01–A02 (синхронизация с v1.1 и вопрос заказчику о коллекции слов) → вертикаль v0 + S1 на железе → A03/A04/A09 и новый дизайн S2 (A08) → заморозка контрактов с узким фасадом оценщика (A05–A07, A13–A14) → упрощения A15–A16 и нарезка задач A17 → остальное по ходу M1.
